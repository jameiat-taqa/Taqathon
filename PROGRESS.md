# Taqathon — Project Log

A running, dated record of what's been done on this project and why. Newest entries at the top. This exists so the history lives in the repo itself, not only in a chat transcript — anyone (human or AI) picking this project up cold should be able to read this and understand the current state and how it got here.

**Convention going forward:** after every meaningful checkpoint (a PR opened or merged, a phase completed, a real bug found and fixed, a significant decision made), add a short dated bullet entry here — what changed, why (if not obvious), what's still open. Committed in the same PR as the work it describes.

## 2026-08-16 — Home page visual system (Design B editorial refresh)

- User asked for a real visual redesign, scoped explicitly to **Home page hero + About sections only** (other 17 pages untouched for now) — supplied 5 mockups and a written brief specifying "Design B": an amber/cream/ink/terra editorial palette using Big Shoulders Display (headings), Tajawal (Arabic display), and DM Mono (labels), loaded page-locally via a new `{% block pageHead %}` slot in `base.njk` so no other page pays for the extra font weight.
- **Bilingual layout was explicitly not decided unilaterally**: user asked for a proposal on how the wordmark/mono-labels/marquee should handle AR/EN before any of it got built. After reviewing the existing bilingual logo as precedent and proposing options, user's answer was simpler than any option offered — **everything single-language, no bilingual treatment anywhere on the page** — and that's what got built.
- **Color/type tokens were pulled into `common.css`** as reusable site-wide custom properties (`--color-amber`, `--color-terra`, `--color-cream`, `--color-sky`, `--color-stone`, `--color-dust`, `--font-display`, `--font-mono-label`, etc.) rather than living only in Home's page-scoped styles, per the user's instruction to build this as a real design system, not a one-page skin.
- **Iterated through 7 rounds of direct design feedback** (colors, structure, motion, section rhythm — see git history on `phase-3-visual-refresh` for the blow-by-blow) before landing on the current structure:
  - Light mode is genuinely light everywhere, including nav and footer — no full-width dark section backgrounds. Three tones do the work: **cream** (Hero, Announcements, About), **sky** (Countdown, CTA band), and a third neutral **stone** (nav + footer — deliberately a tone not used anywhere else on the page, so chrome reads as its own band rather than a near-miss of whatever's directly below it).
  - Dark navy (`--brand-dark`) was demoted from section backgrounds to small accents only: the hero's floating stat bar, the About section's two stat cells.
  - The marquee strip (moving ticker under the About heading) was cut entirely — user felt it added too much motion/color for what it contributed.
  - Every contrast decision (text/background, icon/background, button states) was verified against WCAG 4.5:1/3:1 thresholds with a from-scratch relative-luminance calculation before shipping, not eyeballed.
  - **Content-authenticity rule held throughout**: no invented copy/stats — the About section's numbers are the real prize amounts (joined) and real track count (3), sourced from existing data files, not placeholder text.
- **Real bug caught mid-round**: a CSS comment containing a literal `--brand-*/--surface-*` accidentally closed its own `/* */` block early, silently truncating the comment and dropping the next custom property (`--color-amber`) from the parsed stylesheet — invisible from reading the source, only caught by inspecting `document.styleSheets[...].cssRules[...].cssText` directly in the browser. Fixed, and a standing regex check (flagging any `/* ... */` block under 15 chars) became the routine post-edit verification for this file for the rest of the round.
- **Simultaneous-contrast investigation**: user asked why the nav and footer — both the identical `--color-stone` — looked mismatched. Confirmed via computed-style checks and a clean rebuild that they render pixel-identical (`rgb(244,243,240)`); the perceived difference was simultaneous contrast (nav touches the warm cream Hero, footer touches the cool sky CTA band, so the same color reads slightly differently next to each). Fixed not by changing the color but by adding a faint 1px navy hairline (`rgba(0,40,76,.08)`, with a white-tinted dark-mode equivalent) between the two — gives the eye a hard edge to reset at instead of comparing across a gradient. User liked the result and asked to extend the same hairline to **every section boundary on the page** (navbar→hero, hero→countdown, countdown→announcements, announcements→about, about→CTA, CTA→footer) as a deliberate rhythm device, including between the two same-colored cream sections (Announcements/About) where there's no actual color change — purely for the visual cadence.
- Footer's icon-only social links and headings had their forced `text-white`/`text-light` Bootstrap utility classes removed (`footer.njk`) — harmless when the footer was unconditionally dark, but would have gone invisible once it became theme-aware and light in light mode.
- **Still open**: dark mode for this new structure is explicitly not built yet — the plan (documented in `home.njk`'s own comments) is a mirror of the same structure with navy as the base and light tones demoted to accents, deferred to a later round. The pre-existing color-contrast finding from the accessibility pass (white text on default `--brand-blue`, 3.92:1) also remains open for whenever this same treatment extends to the rest of the site.
- PR [#20](https://github.com/jameiat-taqa/Taqathon/pull/20), open against `dev`, not yet merged.

## 2026-08-13 — Dark mode

- Picked up the next Phase 3 item (split-work session, assigned to Claude Code): a real, toggleable dark mode across the whole site, not just a couple of showcase pages.
- **Mechanism**: driven by `data-bs-theme` on `<html>` — Bootstrap's own color-mode attribute, not a custom one, so Bootstrap's built-in components (modals, dropdowns, accordions, form controls, badges) re-theme themselves automatically via their own `[data-bs-theme=dark]` CSS with zero extra work. A small inline script at the very top of `<head>` (before any stylesheet) sets it synchronously from `localStorage` (an explicit past choice) → else `prefers-color-scheme` → else light, so there's no flash of the wrong theme on load. The toggle button (navbar, next to search) flips the attribute, persists the choice, and syncs its own icon (moon ↔ sun) and `aria-pressed`.
- **Design tokens**: `common.css`'s `:root` gained theme-aware tokens (`--bg`, `--surface`, `--surface-border`, `--surface-hover`, plus `--icon-circle-bg`/`-border`), redefined once under `[data-bs-theme="dark"]`. `--brand-*` colors deliberately stay the same in both modes — they're identity/accent colors, not surface colors. Converted `.card-lite`, `.navbar`, the mobile nav dropdown, `.icon-circle`, and the Pagefind search UI's own CSS variables to read from these tokens instead of bare hex values.
- **Bugs caught during the audit, not just cosmetics**: three places had a background hardcoded to white/light while their own text relied on the (now theme-aware) inherited `--text` color — `contact.njk`'s `.panel`, `sponsors.njk`'s `.sponsor-box`, and — the one that would've been easy to miss — `schedule.njk`'s workshop/key-date table row tints, which had a fixed pastel background but no fixed text color of their own (unlike the section-header rows right next to them, which did). All three would have silently gone light-text-on-light-surface or the reverse the moment dark mode shipped; fixed by giving each either a theme-aware surface token or an explicit matching text color.
- Also caught: the navbar's hamburger icon is a Bootstrap-generated inline SVG tuned for a light navbar (this site pins `.navbar-light`) — its dark stroke color doesn't respond to `data-bs-theme` on its own, so it would've disappeared against a dark navbar. Fixed with a `filter:invert(1)` override under the dark selector. Also swapped `.navbar-nav .nav-link` and both navbar icon buttons from `var(--brand-dark)` to `var(--text)` — brand-dark is the fixed navy identity color (correct for things like the footer, which is deliberately dark in both modes already), but nav text/icons need to actually flip, which only `--text` does.
- **Deliberately left light-styled in dark mode** (self-contained boxes that already set their own fixed text color against their own fixed background, so they're a "these stay as light accent chips" design choice, not a bug): the `alert-info` callout boxes (Registration/Submissions/Community/Newsletter), `badge-soft`, the home page's announcement cards, and the gallery's photo cards. Revisit if/when a full visual-system pass happens, but nothing here is illegible.
- Verified in-browser: light↔dark toggle round-trips correctly, persists across page navigation (no flash), falls back to `prefers-color-scheme` when nothing is stored, checked on Home/About/Contact/Sponsors/Schedule/FAQ/Gallery in both languages — RTL Arabic dark mode, the search modal (including live results), and the FAQ accordion all confirmed themed correctly with no console errors.
- **Open**: rest of Phase 3's visual-system item (typography/spacing beyond color) not started; the still-open button-contrast finding from the accessibility pass (2026-08-13 entry below) is unrelated to this work and remains open.
- PR [#19](https://github.com/jameiat-taqa/Taqathon/pull/19), → `dev` → `main`.

## 2026-08-13 — Phase 3 accessibility pass

- Picked up the next Phase 3 item (split-work session, assigned to Claude Code): a real accessibility audit and fix pass, not just a checklist. Findings and fixes below; a programmatic check afterward confirmed all 36 pages (verify.html excluded, see below) have exactly one `<h1>`, exactly one `<main>` landmark, and a working skip link.
- **Missing `<main>` landmark on Home**: every other page wrapped its content in its own `<main class="py-5">`, but home.njk never did (its content block starts straight with `<section>`s) — meant Home had no main landmark at all, and also wasn't participating correctly in common.css's sticky-footer flexbox rule (`main{ flex:1 0 auto; }`). Fixed at the root instead of patching Home alone: `<main id="main-content" tabindex="-1">` now lives once in base.njk, wrapping `{% block content %}`. Every page template's own `<main class="py-5">` became `<div class="py-5">` (17 files) so there's no more nested/invalid `<main>` inside `<main>`.
- **No skip-to-content link**: added one as the first focusable element on every page (`base.njk`, styled in `common.css`'s `.skip-link:focus` rule, label from new `site.*.json` `skipLinkLabel` field). Targets `#main-content`; `tabindex="-1"` on `<main>` makes it an actual valid focus target after the jump, not just a scroll position — verified in-browser that focus really lands there, not just that the URL hash changes.
- **14 pages had no `<h1>` at all**: 13 pages (FAQ, Tracks, Sponsors, Judges, Submission Guidelines, Community, Newsletter, Registration, Schedule, Rules, Contract, Submissions, Gallery) used a `<h5>` as their only heading — promoted each to `<h1 class="h5 ...">` (same trick already used on About/Past Seasons: semantic level via the tag, visual size frozen via a Bootstrap `.h5` class, zero visual change). Contact was the odd one out — no hero section at all by design, so its first-ever `<h1>` is visually-hidden (new `pageHeading` field in `contact.*.json`, matching the "Contact Us" nav label) and its five `<h6>` panel headers were promoted to `<h2 class="h6 ...">` siblings under it.
- **Unlabeled icon-only controls**: footer's 4 social links (Twitter/X, Instagram, LinkedIn, TikTok — new `social.*Label` fields in `site.*.json`), the language-switch link (new `langSwitch.ariaLabel`), and gallery's per-photo zoom button (built in client-side JS, not Nunjucks — new `zoomButtonAriaLabel` field, plus a missing `type="button"`) all had no accessible name before this.
- **Contact form had no label/input association**: `contract.njk`'s form already did this correctly (`for="full_name"` / `id="full_name"`); `contact.njk`'s four fields (name/email/subject/message) never did — labels and inputs just happened to sit next to each other visually with no programmatic link. Added matching `id`/`for` pairs (`contact-name`, `contact-email`, `contact-subject`, `contact-message`).
- **Color contrast — measured, partially fixed, partially flagged open**: computed WCAG contrast ratios for the brand palette's actual on-page usage (not just eyeballing). White text/icons on a `--brand-green` (#09C899) hover background measured **2.16:1** — badly below the 4.5:1 AA minimum for text and even below the 3:1 minimum for icons — and this exact pattern repeats in 4 places: `.btn-lang:hover` (common.css), `.btn-join:hover` (schedule.njk), `#loadMoreBtn:hover` and `.back-to-top:hover` (gallery.njk). Fixed all 4 by swapping just the hover-state text/icon color to `--brand-dark` (6.91:1, passes easily) — background untouched, so the brand color itself isn't changed, only what sits on top of it in that transient state. **Left open on purpose**: the *default* (non-hover) state of white text on `--brand-blue` (#007DFD) measures **3.92:1** — passes for large text/icons (3:1) but fails for normal-size text (needs 4.5:1) — affecting `.btn-lang`'s resting state, `#loadMoreBtn`'s resting state, and anywhere `--brand-grad`'s green end sits under white text. Fixing this properly means darkening an actual persistent brand color, which is a visual-system decision (Phase 3's still-unstarted "colors/typography/spacing" item), not something to change unilaterally inside an accessibility pass — flagging the exact numbers here so it doesn't get lost.
- **Explicitly out of scope**: `verify.njk` (the certificate-verification page) — it's a deliberately standalone page outside the shared layout, and its rework is already its own separately-deferred piece of work (see the 2026-08-11 entry and this file's earlier notes); not touched here.
- **Open**: the color-contrast finding above; rest of Phase 3 (visual system, dark mode) not started.
- PR [#18](https://github.com/jameiat-taqa/Taqathon/pull/18), → `dev` → `main`.

## 2026-08-11 — Decap CMS OAuth: Netlify dead end found and replaced with a Cloudflare Worker

- The original Phase 0.5 plan (see 2026-08-10 entry) pointed the CMS's OAuth `base_url` at a blank placeholder Netlify site, on the documented-sounding assumption that Netlify's OAuth-provider feature works for any site in a Netlify account.
- **It doesn't.** That feature only works for sites Netlify is actually building and deploying — a blank placeholder 404s. Confirmed by hitting the site's `/auth` endpoint directly (no login needed) and getting Netlify's own generic 404 page, before the request ever reached GitHub. This cost a full round of "it's still broken" with the user before the real cause was found.
- Replaced entirely with **`cloudflare-worker/decap-oauth-worker.js`** — a small, self-hosted OAuth proxy on Cloudflare Workers' free tier. The token-exchange and `postMessage` handoff logic was built against a verified working reference implementation (not guessed), since that handshake is easy to get subtly wrong.
- **Real gotcha hit during setup:** adding the `GITHUB_CLIENT_ID`/`GITHUB_CLIENT_SECRET` secrets via Cloudflare's dashboard did not take effect on the already-deployed Worker until clicking **Deploy** again. Worth remembering if these secrets are ever rotated.
- User confirmed login works end-to-end after this fix.
- PRs [#8](https://github.com/jameiat-taqa/Taqathon/pull/8) (the failed Netlify base_url attempt) and [#9](https://github.com/jameiat-taqa/Taqathon/pull/9) (the working Cloudflare Worker replacement), both merged directly to `main` given the live-site urgency, then reconciled back into `dev`.

## 2026-08-09 to 2026-08-10 — Phase 0: migrated to Eleventy, all 15 static pages → 8 templated page types

- The site used to be 15 hand-duplicated static HTML files (one per page, per language) — editing anything meant finding and fixing it in two nearly-identical files, and they'd already drifted apart in places (missing `aria-label`s, inconsistent classes) purely from human copy-paste error.
- Migrated to **Eleventy + Nunjucks**: one template per page type, Arabic/English content split into JSON data files, built by GitHub Actions into the same flat static HTML GitHub Pages already served (zero URL/SEO breakage). The AR/EN split uses Eleventy's *pagination-over-a-data-array* feature — one template, two output files.
- Done deliberately incrementally, proven on Home first (PR [#3](https://github.com/jameiat-taqa/Taqathon/pull/3)), verified byte-for-byte equivalent to the live site before touching anything else, **then** the remaining 7 page types (Contract [#4](https://github.com/jameiat-taqa/Taqathon/pull/4), then Schedule/Submissions/Rules/Gallery/Contact/Verify together [#5](https://github.com/jameiat-taqa/Taqathon/pull/5)) once the pattern was trusted.
- Real bugs caught and fixed during migration (not introduced by it — found by diffing normalized output against the live pages): a hardcoded `fw-bold` instead of the data-driven `headingClass` on Schedule; a completely missing `<body class="bg-light text-dark">` on Submissions; a misplaced-parenthesis logic bug in the original Contact-EN JS; HTML-entity-escaping corrupting literal text inside `<script>`/`<style>` blocks (Nunjucks auto-escapes `{{ }}` by default, fixed globally via the `| safe` filter with explanatory comments).
- All 15 old static HTML files deleted once the new pipeline was confirmed working in production; GitHub Pages switched from "deploy from branch" to "GitHub Actions" as the build source.
- **Follow-up fix, same window:** the Arabic Contact form was behind the English one in features and used a different, less tolerant success/failure check against the same backend. Unified both to one shared handler (PR [#6](https://github.com/jameiat-taqa/Taqathon/pull/6)).
